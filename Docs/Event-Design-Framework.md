# Event Design Framework

## Purpose

Events add texture, opportunity, and soft friction to the pantry without breaking the cozy promise.

An event is good when it creates a readable choice. It is bad when it simply interrupts production and makes the player clean up a mess they could not predict.

## Event Taxonomy

### Positive Opportunities

- a premium buyer arrives for a potion the pantry can produce
- a helper blessing temporarily speeds one room role
- a rare ingredient appears if the player can route production quickly

Use these to make the pantry feel alive and generous.

### Mixed Soft Friction

- a cauldron overheats and needs a cheap cooling fix
- a shelf gets crowded and slows fulfillment until cleared
- damp weather hurts drying output but helps mushrooms

Use these only when cause, effect, and counterplay are visible.

### Player-Triggered Gambles

- optional rush orders with higher rewards
- unstable recipe variants with previewed risk
- special visitors who trade one pantry advantage for another

Use these when the player chooses the risk knowingly.

## Hard Limits

- no major destructive loss
- no opaque punishment
- no long involuntary downtime
- no event that only makes the UI noisier
- always provide response, counterplay, or a clear reason to ignore it

## UX Rules

- event cause must be clear
- player response must be easy to understand
- rewards and risks must be shown before commitment
- compact mode should summarize the event in one short line
- full view should show the affected machine, room, or contract

## Good Event Test

An event should produce this sentence:

```text
Because X happened in the pantry, I can do Y for Z benefit.
```

If the sentence reads like "a random penalty happened, wait it out," cut or redesign the event.

## Tone Rule

Events should feel like magical pantry life: mischievous, useful, recoverable, and readable.
